# 任务原图（原生）

「任务原图」把**截图库里已经归档的原图**显式关联到某条任务，回答两个问题：

1. 这条任务关联了哪些原图？
2. 能不能从既有截图库里再挑一张加上，或解除一条**手动**关联？

图片本身不会复制、不会重新上传、不会识别，也不会改动任务的截止时间、状态或来源文本。

## 从哪里进

- 「任务」标签页 →「任务详情」→「任务原图」；
- 「今天」标签页 →「任务详情」→「任务原图」。

两条标签页各有自己的原生栈，因此从任意一条进去，返回手势与返回按钮都正常。
路由名是 `TaskPhotos`，参数是 `{ id: number }`（任务 ID），两条栈共用同一个界面。

## 使用流程

1. 打开时读取这条任务已关联的原图，以及截图库里最近保存、还没有手动关联到这条任务的原图。
2. **查看**：点缩略图或「全屏查看」进入全屏，可双指缩放；显示的是截图库里归档的那份原图字节，不是相册临时地址。
3. **添加**：在「从截图库添加」里点某一张的「添加」。一次只添加一张，只有这一下会写入。
   - 最多显示最近保存的 300 张可添加原图；已经手动关联到这条任务的不再列出。
   - 没有自动选择、没有批量勾选草稿、没有“打开页面就顺手关联”。
4. **解除关联**：手动关联的原图有「解除关联」。确认框会明确写：
   「只解除这条任务的关联，原图仍保留在截图库。」
   确认后只删除这条任务上的这一条手动关联；原图文件、OCR 结果、课程 / 课表 / 其它任务 / 历史引用都不动。
5. 回到这一页会重新读取列表；如果任务在别处被删除，页面显示「这条任务已经不在本机了」，不能再添加或解除。

## 历史关联与手动关联

- 本模块新增的关联关系固定为 `MANUAL_TASK_PHOTO`，只有它是用户可解除的。
- 同一张原图可以独立关联到两条任务；解除一条不会影响另一条。
- 既有的非手动任务引用（例如历史 `SOURCE` 关系）仍会出现在列表里，但标为「历史关联（只读）」，
  不会显示「解除关联」，也不会被误删。
- 截图库里没有删除入口；本模块也不删除任何图片文件或 OCR 结果。

## 存储与校验

复用既有 `screenshot_refs` / `screenshot_attempts`，**没有迁移、没有新表、没有新依赖**。

- 添加 / 解除都在**一个事务**里：事务内先确认任务还在、原图仍在截图库里、`archived_path` 非空且状态不是
  `ARCHIVE_FAILED`，再写 / 删那一条引用。
- 重复添加是幂等的：同一条任务里的同一张原图（按尝试或按归档文件识别）只保留一条手动引用。
- 识别失败 / 取消（`FAILED` / `CANCELLED`）但原图已经归档的尝试**可以**关联；没有归档文件、
  归档失败或根本不存在的原图会被拒绝，零写入。
- 任务被删除后，读取返回「任务不在」，添加 / 解除都会被事务拒绝；删除任务不会删除原图、OCR 结果或历史引用。
- 读取只走查询：打开页面、列候选、列已关联都不会写库。

## 刷新、并发与失败

- **聚焦时重新读取**已关联与可添加列表；读取中 / 读取失败时不允许写入。
- **React 生命周期安全**：`TaskPhotosScreen` 的 effect setup 先 `activate()` 再订阅并补一次新鲜读取，
  cleanup 先退订再 `dispose()`。StrictMode / Fast Refresh 的 setup → cleanup → setup 不会把控制器永久废掉；
  重挂会作废旧读回 / 旧写入回调、清掉 busy / loading / 旧快照，并在新读取成功前禁止写入。
  旧的在途写入可能完成一次存储动作，但不能再改新状态或放掉新写入的闸门，也不会重放添加 / 解除。
- **同步在途闸门**：写入开始前先置位，同一帧双击不会发第二个写请求；
  切换任务后，旧任务写入完成不会提前放掉新任务正在进行的闸门。
- **迟到的读取不会盖掉当前任务**：每次读取有序号；切换任务或离开页面后，旧读回被忽略。
  切到无效任务编号时页面直接变成不可写，不会把旧任务留在可写位置。
- **写入已提交、但随后的本页列表刷新失败**：页面明确说「这次操作已经保存好了」，
  只提供「重新读取列表」，不允许重复添加 / 解除；提交这个事实不会被刷新失败改写。
- **写入已提交、但任务全量快照刷新失败**：仍按成功提示，并单独显示
  「关联已经保存，任务列表刷新失败」，只提供重新读取，不把它说成添加 / 解除失败。
  在任务列表重新读取成功之前，写入按钮保持禁用。
- 没有归档路径或 `Image` 加载失败：全屏查看器会明确显示「这张原图在本机找不到了」/「这张原图打不开」，
  并提供「重新加载图片」/「重新读取」「关闭」，绝不假装图片还在；换一张图会清掉上一张的加载错误。
- 全屏查看器复用既有安全区组件，顶部关闭与底部操作在 iPhone 上不会被刘海 / Home 指示条压住。
- 普通读取失败会显示错误与「重新读取」，不会把「读不出来」显示成「还没有关联」，
  错误态下也不会渲染空列表或允许写入。

## 刻意不做的事

- 不上传、不重新识别（OCR）、不拍照、不读写新的图片文件；
- 不自动把截图关联到任务，也不根据 OCR 结果自动匹配；
- 不改任务状态、DDL、预计用时、原始文本或来源；
- 不改任务删除语义，不做通用删除，不删除历史 / 课程 / 其它任务引用；
- 不做批量多选、AI、提醒、日历联动。

## 验证

- 新增测试 41 条：真实 SQLite 仓库 11、运行状态机 15、接线 15。
- 生命周期修复后按复核要求只跑变更面：控制器 + 接线 **30 / 30 通过**、`tsc --noEmit` **0 error**、
  两个 immutable oracle **6/6 + 3/3 PASS**。上一轮受影响既有文件的 158 / 158 未重跑
  （本轮没有改仓库逻辑或其它模块）。
- 真实 SQLite 覆盖：添加 / 读取 / 关库重开、重复添加幂等、同一张图两条任务、解除只删目标手动引用
  （保留原图 / OCR / 课程 / 历史 / 其它任务）、无路径 / 归档失败拒绝、识别失败但原图仍在可关联、
  非法 / 缺失 ID、任务删除后拒绝写入、注入写入失败整体回滚、候选上限与排除、读取零写入。

**限制**：上述 SQLite 是 Node 侧 `node:sqlite`，验证 SQL 与事务 / 状态逻辑，验证不了 iPhone 上的
`expo-sqlite` 原生绑定、真机手势与视觉布局；本轮没有在模拟器 / 真机上跑界面，也没有启动或重启
Metro / 识别服务。测试只使用系统临时目录与内存库，不碰真实用户数据。
