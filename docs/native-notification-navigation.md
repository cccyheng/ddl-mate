# 原生任务提醒点击 → 任务详情

更新：2026-10-21。状态：**真实手机上已确认收到本机通知；点击通知没有正确打开任务详情，修复后等待同一台手机复测。**
范围：只处理本应用任务提醒 / 测试提醒被点击后打开对应已有任务；不是云推送，不修改任务状态，也不打开提醒设置。完整通知规则见 [`native-task-reminders.md`](./native-task-reminders.md#7-点击通知)。

## 1. 已确认与未确认

- **已由用户确认**：真实手机上通知能送达（收到测试提醒）。
- **已由用户确认**：点击后没有正确打开任务详情；但当时是停留在原页面、看到编辑暂缓 banner，还是 Expo Go 回到首页 / 打开错任务，**尚未得到答复**。
- 代码审查发现两个**有证据的缺陷**（见 §3），已修复；它们不是「手机失败原因已证实」的唯一结论。
- 修复后**尚未在同一台手机上复测点击**；不能声称真机点击已验收。

## 2. 行为

- 点击本应用任务提醒或 `...v1.test.<taskId>` 测试提醒 → 切到「任务」标签并打开对应任务详情。
- 只认严格命名空间与载荷：通知 ID、任务 ID、正式 fingerprint / 测试 triggerAtMs 必须一致；只认系统默认点击动作。
- 只把正整数 taskId 交给导航，固定 `Tasks → TaskDetail`，`initial: false`；不解析 URL 或任意路由名。
- 任务是否存在用**只读 fresh 数据库查询**判断：内存快照没有 ≠ 已删除；读失败显示可重试错误，不导航、不写回执。
- 不调用 `clearLastNotificationResponse`；改用 `app_settings` 中有界（32 条）的已消费回执，避免误清用户刚点的下一条通知。
- 回执 token = 通知 ID + 展示时间 + 已验证载荷证据 + 动作。支持重启去重、A → B → A 不重复；同一稳定 ID 的新日期 / 新载荷视为新投递。
- 缺 / 非法展示时间不写持久回执，只用 5 秒内存窗口去掉监听器 + last 的重复事件，窗口过后的新投递仍可打开。
- **导航落地确认**：`navigationRef.navigate(...)` 不返回「是否被处理」。现在会等待根状态里真的出现**目标任务详情**才写回执；导航被静默忽略或落到错误任务时显示可重试错误，**不写假回执**。
- 回执写失败只显示 warning，不谎报已持久化。

## 3. 本次手机失败修复（证据-backed，非唯一已证实原因）

1. **干净详情 / 提醒页被误判为编辑中**：旧实现只要 Tasks 栈里出现 `TaskDetail`（或聚焦 `TaskReminder`）就一律暂缓。用户只是正常查看详情、或刚从详情进入提醒页点「测试提醒」时，点击会被静默挡在 banner 后面。现在这两个页面只在**真实未保存状态**时阻塞：
   - 任务详情：追加原文有字、删除确认框打开、正在写库（busy）；
   - 提醒设置：设置 dirty 或正在保存（busy）。
   - 表单 / 导入 / 核对页仍按路由名保守暂缓。
2. **导航未被确认就写回执**：旧实现调用 `navigate` 后立即认为成功。现在等 `TaskDetail(id)` 真正成为当前路由；超时 / 错误可重试，且不写回执。
3. **任务详情按 task id 生成路由 key**（`getId`）：不同任务得到独立详情实例；同一任务不会重复堆叠。干净详情实例被复用于另一条任务时，旧的 toast / 输入 / busy 会被清掉；真实草稿绝不清掉。

## 4. 草稿保护

以下路由**始终**视为「可能有未保存内容」，通知到达时只显示非破坏性 banner，不导航、不 pop、不弹草稿确认：

`TaskForm / CourseForm / ScheduleForm / NoticeImport / NoticePhoto / BatchNotice / PhotoReview / TaskSteps / TodayPlan / Pressure`

`TaskDetail / TaskReminder` 改为**草稿感知**：

- 当前聚焦路由命中，或 **Tasks 标签的栈内任意层级**命中，都会暂缓；即使用户在日历 / 今天 / 课程标签，隐藏的 Tasks 表单 / 草稿详情也不会被覆盖。
- 干净的详情页、刚点完测试提醒但没改设置的提醒页**可以正常打开**。
- 草稿登记按真实 route key；卸载清理延迟到微任务，StrictMode cleanup → setup 或 dirty→dirty 不会瞬时报「干净」。
- banner 文案提示「先完成当前编辑，离开后自动打开」；编辑中不提供会丢草稿的直达按钮。
- 用户正常返回 / 离开后 controller 才交付排队点击；不强制重置导航栈。
- 任务已删除时显示「任务已不在本机」，不打开空详情；「返回任务列表」只在非编辑、导航就绪时可用。

## 5. 本机诊断（无正文 / 不联网）

为定位「收到通知但点了没打开」，提醒设置页新增紧凑的「通知点击诊断」：

- 默认一行人话摘要，例如「已打开任务详情（任务 #7）」「已识别，但「提醒设置」有未保存内容，稍后打开」「打开失败：导航没有真正打开任务详情」；
- 可展开看最近点击来源、阻塞页、导航目标、持久回执、本机通知模块 / 冷启动读取状态；
- 固定构建标记 **`phonefix-20261021-1`**，便于确认手机跑的是哪一版；
- **不记录**通知标题 / 正文 / 原始 payload / 凭据；不写库、不联网、不调用第三方；
- banner 在待打开 / 错误时也显示同一摘要。

## 6. 限制

- **真实 iPhone 的点击跳转复测尚未完成**；已确认送达，不等于已确认点击导航。
- Expo Go 被点通知后的容器行为（是否回到 Expo Go 首页、是否重载项目）仍未确认；诊断只能记录 JS 侧实际收到了什么。
- 冷启动点击依赖原生 `getLastNotificationResponse`；具体展示与点击行为由 iOS / Expo Go 决定。
- 没有远程推送、APNs、EAS、push token、后台 JS 同步；已排好的通知不依赖后台 JS 触发。
- 未改 DB schema / 版本；回执复用 `app_settings`。未新增依赖。

## 8. 手机复测步骤（Codex / 用户）

1. 在同一台手机、同一 Expo Go 项目上确认提醒设置页底部显示构建 `phonefix-20261021-1`。
2. 任务列表 → 任务详情（不要输入「追加原文」）→ 提醒设置 → 点「测试提醒（10 秒后）」；停在提醒页或返回任务列表。
3. 通知到达后点击：
   - 应打开「任务」标签下对应任务详情；返回应回到任务列表或来路；
   - 若仍停留原页面 / 看到 banner，请把诊断摘要一行（或展开详情）报告给复核者；
   - 若 Expo Go 回到首页，也请明确说明，这属于容器行为，不能当作导航代码已通过。
4. 在任务详情「追加原文」输入文字 / 打开删除确认框时点提醒：应只出现暂缓 banner，不跳走、不丢草稿；清空 / 关闭后应自动打开。
5. 隐藏的 Tasks 表单场景：在日历标签、Tasks 栈里压着未保存表单时点提醒，不应 pop 表单。
6. 删除任务后点旧通知：显示「任务已不在本机」，不打开空详情。
